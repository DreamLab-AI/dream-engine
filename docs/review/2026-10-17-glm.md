### R-1 — The night recorded a verdict for a change that was never published (or merged without protection)
- Topics: CRT-02.1, CRT-02.2
- Chain of events:
  1. The host driver finishes evaluation and calls `publish_draft` and optional automerge through the engine's persist path (`crates/dream-core/src/persist.rs:298`).
  2. The `GhForge` push, PR-creation or branch-protection call fails — an expired token, a changed GitHub API, a protection rule that was never actually applied. These paths have never been exercised against a live GitHub at all.
  3. The failure is returned *inside* the `PrOutcome`, never raised, and the night proceeds to record its verdict anyway.
  4. The memory write is best effort ("log and continue") and notification is infallible by signature, so the failure surfaces nowhere durable — at most a stderr line.
  5. The client's repository never receives the fix, or receives it automerged without the intended status checks. The operator only learns of this from the client.
- Evidence: "A forge failure is reported inside the `PrOutcome`, never raised, so the night still records its verdict" (`crates/dream-core/src/seams.rs:365`). "`GhForge` has one test in this tree and it only proves the trait is dyn-safe… The push, PR creation and branch-protection paths have not been exercised against a live GitHub" (`crates/dream-core/src/seams.rs:647`, author-flagged Debt). Best-effort memory (`crates/dream-core/src/seams.rs:147`); infallible notify (`crates/dream-core/src/seams.rs:320`).
- Warning signs visible today: the Debt flag on the only forge test; the explicit "never raised" swallowing semantics; two consecutive reporting channels (memory, notifier) that are each incapable of escalating.
- Confidence: medium, inferred
- Severity: high

### R-2 — The audit trail of what the engine did to the client's code does not survive
- Topics: CRT-02.1, CRT-02.2
- Chain of events:
  1. A night runs with the shipped `JsonlSink` (or an unwired host falls back to `NullSink`).
  2. The write fails — disk full, permissions, path gone. Callers "log and continue"; the night's record of prompts, patches and verdicts is simply absent.
  3. The notifier cannot report the loss: its signature is infallible, so an implementation has no way to signal failure through the API.
  4. When the client disputes what was done, the operator cannot produce the record. The gate's advertised replayability is useless, because replay needs the recorded inputs that were never durably stored.
- Evidence: "Memory writes are best effort and callers log and continue" (`crates/dream-core/src/seams.rs:147`); `NullSink` and `JsonlSink` are the shipped sinks (`crates/dream-core/src/seams.rs:157`, `crates/dream-core/src/seams.rs:202`); "`Notifier::notify` is infallible by signature, so a broken channel cannot change a verdict" (`crates/dream-core/src/seams.rs:320`); the gate "can stay a pure function that a replay can re-run" (`crates/dream-gate/src/gate.rs:8`) — a promise with no matching durability promise for its inputs.
- Warning signs visible today: two of the three reporting seams are explicitly designed to be lossy; the replay promise in CRT-01.1 has no counterpart durability requirement anywhere in the material.
- Confidence: medium, inferred
- Severity: high

## Not judgeable from this material

1. Provenance and integrity of the frozen manifest — who freezes it, whether the model or candidate process can influence its required-evaluator list, command digests, or extras, and whether it is authenticated. The entire gate is a pure function of this input; its custody is decisive for F-05, F-06 and F-07.
2. How `tree_trusted` and the tree hash are computed — whether the recorded tree is cryptographically bound to baseline plus applied patch. `decide` re-checks patch text (`gate.rs:420`), never tree contents, so acceptance integrity rests on an input whose derivation is not shown.
3. The runner's actual isolation — user, container, namespace, network policy for the build and evaluator processes. The Debt says "isolation is the host's job", but the host's controls are undescribed, which determines the real blast radius of F-01 and F-02.
4. Concurrency control and crash semantics — whether hosts serialise candidate runs per repository/branch, how git behaves with two worktrees on one branch, and what attempt/receipt state `persist.rs` durably records and what a restart mid-night loses or re-runs. This decides whether F-04 and F-15 are live.
5. The model's verdict vocabulary and downstream accounting — which non-ACCEPT readings exist (does a model-issued BLOCKED-ENV pass through verbatim per `gate.rs:493`?) and how INCONCLUSIVE versus BLOCKED-ENV nights are counted, retried, or billed. Post-mortem. Written from the stamped distillation at commit `0f6a66913c072603b6e29a80bdc67350737b9b21`. Every claim below cites the material; where I reason past what the text states I mark it inferred. No source code beyond the citations was available.

## Root causes, most likely first

### R-1 — Candidate-authored code executes with the runner's privileges on the evaluation host
- Topics: GAT-01.3
- Chain of events: A candidate patch adds or modifies a script that the fixed pipeline executes — a build entry file, a repo-local helper, anything the optional candidate build command or a required evaluator invokes. The guard checks only the *patch text* against protected paths (`crates/dream-core/src/candidate.rs:245`, `crates/dream-core/src/persist.rs:139`, `crates/dream-gate/src/gate.rs:420`), so adding new executable content is not itself a violation. The optional candidate build command then runs it (`crates/dream-core/src/candidate.rs:296`), followed by the required evaluators (`crates/dream-core/src/candidate.rs:300`), both through the runner, with the runner's privileges. The script reads what the runner can read — credentials for the git remote, other worktrees, receipt storage, the manifest — and exfiltrates or rewrites it.
- Evidence: The material states this outright as Debt: "a candidate-added build script still runs with the runner's privileges; isolation is the host's job" (`crates/dream-core/src/candidate.rs:296`). No isolation layer appears anywhere in the three flow diagrams; the only containment mechanism in the entire topic is protected-path checking of patch text. The policy is built from the *baseline* config (`crates/dream-core/src/candidate.rs:141`), so the candidate cannot weaken the rules — but the rules only constrain which paths a patch may touch, not what executed code may do.
- Warning signs visible today: The Debt sentence itself, and the fact that the guard's entire threat model is textual (patch bytes, header lines, file counts — `crates/dream-gate/src/guard.rs:977`–`1009`) while the execution model is arbitrary (any script the fixed commands reach). "Isolation is the host's job" is a deferred control with no owner in the diagrams.
- Confidence: high that the defect exists (stated verbatim); the specific breach chain is inferred.
- Severity: high

### R-2 — Unprotected indirect harness files let a candidate forge its own green light
- Topics: GAT-01.5, GAT-01.1
- Chain of events: A candidate patch modifies a file the evaluator reads *indirectly* — a `conftest.py` behind `pytest`, a `Makefile` target behind `make test`. The frozen command `pytest` contains no path-like words, so `word_path` derives no protection from it (`crates/dream-gate/src/guard.rs:586`); the file is not in the config's `protected` globs; the patch applies cleanly. The evaluator runs on the candidate tree (`crates/dream-core/src/candidate.rs:300`), auto-loads the tampered harness file, and the tampered harness neutralises the checks and produces normal-looking passing output. The receipt is genuine: the command digest matches the frozen manifest (`crates/dream-gate/src/gate.rs:218`). `veto_for` sees a `Passed` outcome and produces no veto (`crates/dream-gate/src/gate.rs:123`). `decide` finds an empty veto list with a claimed ACCEPT and returns ACCEPT (`crates/dream-gate/src/gate.rs:489`). The malicious payload rides the same patch into the repository.
- Evidence: The Debt line names the gap exactly: "the reader cannot see files an evaluator reads indirectly (a `Makefile` behind `make test`, a `conftest.py` behind `pytest`); those must be named in the config's `protected` globs" (`crates/dream-gate/src/guard.rs:703`). The business text claims "a test result that has been tampered with … is treated as a broken test machine" — but the tamper detection described is receipt-versus-manifest (`crates/dream-gate/src/gate.rs:197`–`228`), which a harness-file tamper fully satisfies with a valid receipt. The silent-evaluator rule (`crates/dream-gate/src/gate.rs:128`) does not help: the tampered harness prints output.
- Warning signs visible today: The Debt sentence; the fact that protection from commands is limited to "path-like words and known baseline files" (`crates/dream-gate/src/guard.rs:586`), which for `pytest`/`make`/`cargo test` style commands is an empty set, leaving the entire protection burden on operator-maintained globs every night.
- Confidence: high that the protection gap exists (explicit); medium — inferred — that it produced a forged ACCEPT in production.
- Severity: high

### R-3 — Predictable, pre-removed worktree path under the shared temp directory
- Topics: GAT-01.3
- Chain of events: The candidate worktree lands at `dream-wt-<8 hex of the repository path digest>-<branch>` under the shared temp directory, and "any existing directory at that path is removed before use" (`crates/dream-core/src/persist.rs:142`). Two failure modes follow. (a) Cross-user: another local user pre-creates or races that path; between the removal and the worktree creation the attacker controls the directory contents, and a checkout into a directory seeded with symlinks writes outside the tree — or the pre-removal itself deletes attacker-chosen content. (b) Same operator: two concurrent nights on the same repository and branch deterministically share the path — no hash collision needed, the branch component is predictable — and one run removes the other's in-flight worktree, producing a partial or wrong tree that is then evaluated and graded.
- Evidence: Stated as Debt: "On a multi-user host another local user can pre-create or race that path; the patch file that used to sit beside it is gone, but the worktree directory is not yet unpredictable" (`crates/dream-core/src/persist.rs:142`). The prior symlink fix covered only the patch file, by feeding verified bytes to `git apply` on stdin (`crates/dream-core/src/git.rs:23`, `crates/dream-core/src/persist.rs:168`) — showing this attack class was already realised once against this system. The digest is 8 hex characters, i.e. 32 bits, with no per-run salt.
- Warning signs visible today: The Debt sentence; the 32-bit digest; the branch-keyed naming; the history of a sibling symlink vulnerability at the same directory.
- Confidence: high that the weakness exists (stated); the exploitation and self-collision scenarios are inferred (the material asserts removal and predictability, not the race outcome).
- Severity: high

### F-02 — A crash after `Persisted` silently loses the publish, and the restart records `Complete` without asking the forge

## Not judgeable from this material

1. **Journal write durability and atomicity** — whether the run-state save is temp-file+rename and `fsync`ed before the forge push. If `Persisted` can be lost to power failure after the push, the at-most-once claim degrades to duplicates, which is worse than the documented loss direction (F-02/F-06).
2. **The actual host driver** — its source, tests, and whether it takes the night lock, calls `capture`, orders persist before effects, and makes the model call/push idempotent per night key. The repo ships none of the sequencing that every business guarantee rests on (F-04, F-06, F-08).
3. **Deployment topology and night-directory conventions** — single host or many, per-date directories, shared filesystem. This decides whether the per-directory `flock` delivers the claimed exclusion and whether `WrongNight` can fire in normal operation (F-05).
4. **Which side evaluator-supplied `PolicyExtras::protected_paths` and evaluator configs are resolved from (baseline vs candidate), and the default protected set** — i.e., whether a candidate can weaken its own guard or the CI definitions that automerge trusts (F-01, F-15).
5. **Ledger semantics and forge details** — what branch/file the "ledger commit" lands on and when; whether `enable_automerge` targets non-draft PRs and what performs the draft-to-ready transition. Needed to judge the exploitability of F-01 and the reconciliation gap in F-02.

### R-1 — A crash after the journal says `Persisted` silently swallows an accepted change; the restart reports the night `Complete` without asking the forge
- Topics: NIT-01.1, NIT-01.3, NIT-01.4, NIT-03.2
- Chain of events: night gates to ACCEPT → host calls `persist` → journal advances to `Persisted` **before** any external effect → the process dies (reboot, OOM, kill) in one of the three documented windows: before `publish_draft`, after the push but before the PR URL is recorded, or before the ledger row is written → nothing anywhere records the forge push or the ledger commit → restart calls `begin`; `finished_night` is night-level and ignores the run id, so the answer is `AlreadyComplete`, and `Persisted` is finalised to `Complete` best-effort, without reconciling against the forge → the client's accepted change never ships while every record says the night succeeded; the only recovery is a manual operator `reset_night`, and detection depends entirely on a human noticing the absence of a PR.
- Evidence: `Persisted` is "deliberately entered first, so a crash can lose a publish but never repeat one" (runstate.rs:72); "Nothing records the forge push or the ledger commit either, so a crash after `Persisted` loses that night's publish and the restart finalises the night to `Complete` without reconciling against the forge" (runstate.rs:615, runstate.rs:401); the debt restates the windows — "whether before the pull request exists or after it exists but before its URL or ledger row is recorded" (persist.rs:298, runstate.rs:615); finalisation "is best effort and the answer does not depend on the write landing" (runstate.rs:419); the business text concedes it: "The price of never repeating a publish is that a crash at the wrong moment can lose one."
- Warning signs visible today: both governing topics carry authored Tension/Debt saying exactly this; "the night key `(repo, date, night_id)` is the idempotency key for **any future** reconciliation" — i.e., none exists; even where replay `capture` ran, `verify` re-derives the gate decision, not delivery, so it would pass on a night whose PR never existed (NIT-02.2).
- Confidence: high (the loss window and the non-reconciling restart are stated, not inferred).
- Severity: high

### R-2 — The night lock is a documented contract that nothing enforces; two engines can work one night and both publish
- Topics: NIT-01.4, NIT-01.2
- Chain of events: a deployment overlap (cron jitter, a retry after a page, a second host) starts two engine processes on the same night directory → `begin` does not take the `NightLock` and "nothing else in this repository calls `NightLock::acquire`, so an engine that skips it is not stopped here" → either both engines read an absent journal (both `Fresh`), or the later one reads the earlier's `Initialised` record and is told `Resumed` — and both `Fresh` and `Resumed` "say proceed" (runstate.rs:154) → both run the night, both `persist`, both publish; the night key is not used as a forge idempotency key today → on an automerge-opted repo whose facts satisfy `decide`, both pull requests can merge: two divergent candidates from one night land unreviewed.
- Evidence: the lock "spans check, freeze, execute and persist, so two engines cannot both read an absent journal and both publish" (runstate.rs:248) — the stated protection is the lock and only the lock; the Open note that `begin` does not take it and no in-repository caller exists (runstate.rs:261); the resumed path that would tell a second engine to proceed (runstate.rs:549, runstate.rs:557); the unused idempotency key (NIT-03.2 Debt).
- Warning signs visible today: the Open note itself; that the lock already needed fork-child retry handling (runstate.rs:295) shows deployment-level processes around the lock were a live concern.
- Confidence: medium (inferred — the unenforced contract is stated; the two-engine deployment is reasoned beyond the material).
- Severity: high

### R-1 — A fault-heavy candidate accumulates zero evidence vetoes, because policy `Inconclusive` is dropped and the one remaining guard is not proven equivalent to the crate's fault handling
- Topics: SEL-01.1, SEL-01.3
- Chain of events:
  1. During the nightly comparison, a large fraction of the candidate's tasks come back with outcomes but no score; at the crate level these are faults.
  2. The tally excludes them — a fault "is never a win or a loss" (`crates/pairwise-gate/src/model.rs:205`); the guard sees a fault share above 0.5, or fewer than 1 comparable, and returns `Inconclusive` before any rule is consulted (`crates/pairwise-gate/src/policy.rs:39`).
  3. `pertest` maps only a policy `Reject` to an evidence veto; a policy `Inconclusive` "adds no veto at all" (`crates/dream-gate/src/pertest.rs:304`). Per-test evidence "can only add vetoes" (`crates/dream-gate/src/pertest.rs:12`), so with no other veto the layer is silent.
  4. The only remaining barrier is the step-1 harness veto on "any fault, or a baseline test missing on candidate" (`crates/dream-gate/src/pertest.rs:214`).
  5. The material itself warns the two layers "are not obviously equivalent". Any fault representation that reaches the crate guard but not the per-test fault check in step 4 leaves the night with no veto of either class.
  6. If promotion is veto-absence, as the additive design implies (the material does not state any positive-evidence requirement at the nightly level), the candidate ships with its real regressions never counted as losses (`crates/pairwise-gate/src/lib.rs:9`), and produces incorrect client-facing output.
- Evidence: fault-not-loss `crates/pairwise-gate/src/lib.rs:9`; guard `crates/pairwise-gate/src/model.rs:283`, `crates/pairwise-gate/src/policy.rs:39`; only `Reject` acted on and the equivalence doubt, both in the SEL-01.3 Tension note at `crates/dream-gate/src/pertest.rs:304`; harness veto conditions `crates/dream-gate/src/pertest.rs:214`, `:232`; additivity `crates/dream-gate/src/pertest.rs:12`.
- Warning signs visible today: the SEL-01.3 Tension paragraph states the drop of `Inconclusive` and the unproven equivalence in plain words; the guard sits before the rule (`crates/pairwise-gate/src/policy.rs:39`), so fault-heavy evidence can never reach a rejecting rule.
- Confidence: high that steps 1–4 are the stated design; medium, inferred, for step 5's concrete mismatch and for the promotion semantics in step 6.
- Severity: high

### R-2 — A genuinely new failure inherits an unrelated baseline failure's fingerprint and is classified `Persisting`, so the new-failure veto stays silent and the candidate is promoted
- Topics: SEL-02.1, SEL-02.2, SEL-02.3, SEL-01.3
- Chain of events:
  1. The candidate introduces a failure whose cause text normalises identically to an unrelated baseline failure in the same task and stage: digit runs become a number placeholder, long opaque ids and paths become placeholders (`crates/failure-fingerprint/src/lib.rs:190`), causes are truncated at 200 characters before hashing, or the two causes genuinely collide in the 64-bit identity (`crates/failure-fingerprint/src/lib.rs:263`, `:365`).
  2. The fingerprint is the first 8 bytes of SHA-256 over task, separator, stage, separator, normalised cause (`crates/failure-fingerprint/src/lib.rs:357`, `:365`) — same task, stage and normalised cause means the same identity, by construction.
  3. `advance` from the baseline manifest classifies the record `Persisting`, keeping the baseline's `first_seen_step` (`crates/failure-fingerprint/src/lib.rs:576`).
  4. The gate vetoes only `New` records (`crates/dream-gate/src/pertest.rs:255`, `:261`); "persisting and fixed records never veto" (SEL-02.3).
  5. Whether the pairing-based `NoRegression` in the policy stack (`crates/dream-gate/src/pertest.rs:326`) independently catches the failure is not stated in the material; where the failure does not move the pair's scores, the fingerprint veto is the only stated guard.
  6. The promoted candidate carries a new failure mode into production.
- Evidence: the authors' own words — a collision "would classify the new one as `Persisting` and let it past the gate's new-failure veto, with no signal", and ADR-DE-004 lists a collision seen in practice as its review trigger (`crates/failure-fingerprint/src/lib.rs:263` note); normalisation rules `crates/failure-fingerprint/src/lib.rs:190`; hashing `:357`, `:365`; Persisting semantics `:576`; veto mapping `crates/dream-gate/src/pertest.rs:255`, `:261`.
- Warning signs visible today: the SEL-02.1 Tension note; the placeholder rules themselves, which map distinct causes onto one normalised form; the 200-character truncation; the 64-bit identity.
- Confidence: high that any fingerprint match produces the silent bypass (stated); medium, inferred, that placeholder-merging or truncation produces such matches in this suite; low for a raw 64-bit collision as the trigger.
- Severity: high

### R-3 — Credential material in a failure cause survives the normalisation heuristics and is persisted indefinitely in a per-repo manifest in the shared state directory
- Topics: SEL-02.1, SEL-02.2, SEL-02.4
- Chain of events:
  1. A failure cause embeds a secret that is not path-shaped, not matched by the long-opaque-id heuristic, and not a bare digit run — for example a short alphanumeric key.
  2. `normalize_cause` alters only paths, long opaque ids, digit runs and whitespace, and truncates at 200 characters (`crates/failure-fingerprint/src/lib.rs:190`); everything else passes through.
  3. The invariant is that the persisted cause is always the normalised text — i.e. whatever survives is stored verbatim (`crates/failure-fingerprint/src/lib.rs:410`).
  4. The cross-night use writes observations to a per-repo manifest file in the shared state directory (`crates/dream-core/src/streak.rs:94`) and keeps records for as long as the failure persists (SEL-02.4 Open).
  5. Any reader of the shared state directory obtains the credential, and the record outlives the incident for as long as the failure keeps recurring.

- Confidence: low, inferred — no leak is shown; the defect is the gap between the stated heuristic and secrets in general.
