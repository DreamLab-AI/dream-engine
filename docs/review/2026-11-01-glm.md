## crates / critical

### F-01 — The publishing actor both defines its own required status checks and enables automerge, on a code path never run against live GitHub
- Topics: CRT-02.1, CRT-02.2
- Evidence: The `Forge` trait exposes `publish_draft`, `required_status_checks`, `pr_base_branch` and `enable_automerge` together (CRT-02.1); `GhForge` implements it via `git push` and `gh` CLI (`crates/dream-core/src/seams.rs:424`). The authors' Debt states GhForge has one test that "only proves the trait is dyn-safe" (`crates/dream-core/src/seams.rs:647`) and that "push, PR creation and branch-protection paths have not been exercised against a live GitHub." No human-review step appears anywhere in the material; the sequence ends at publish/automerge (CRT-02.2).
- Failure: First live exercise of `enable_automerge`/`required_status_checks` is the first production night. If the untested call sets an empty or wrong check list while automerge is on, an LLM-generated patch merges to the base branch with no effective gate and no human in the loop.
- Confidence: high that the methods are co-located and untested; the self-gating failure mode is inferred
- Severity: high
- Marked by authors: partially — Debt covers the untested GhForge; the automerge-plus-self-configured-checks combination is unmarked

### F-02 — "Host contains faults" is asserted as the design, but no driver exists in this repository to contain anything
- Topics: CRT-02.2, CRT-02.1
- Evidence: The sequence note says "notify with no Result - host contains faults" (CRT-02.2), yet the Open marker admits "No driver in this repository enforces it [the intended order]… the order is not machine-checked here" (`crates/dream-core/src/lib.rs:3` cited as source of the order). The business text concedes "A full night still needs a host driver."
- Failure: Whoever adopts this writes the orchestrator — the component that owns crash handling, persistence timing and fault containment for an agent that can merge code — from scratch, with zero reference implementation and no machine-checked contract. Every containment property in these documents is then unverifiable at review time.
- Confidence: high
- Severity: high
- Marked by authors: yes (Open)

### F-03 — The night's ledger is a single best-effort write that happens after the PR is already live
- Topics: CRT-02.2, CRT-02.1
- Evidence: The asserted order is publish first, then "record the night, best effort" (`crates/dream-core/src/persist.rs:291` for publish; CRT-02.2 sequence). Memory writes are best effort and "callers log and continue" (`crates/dream-core/src/seams.rs:147`); "persistence of the night is a separate host responsibility" (CRT-02.2). Recording appears exactly once, at the end.
- Failure: Memory-sink failure or a crash anywhere between `publish_draft` and the final write leaves a published (possibly automerged) PR with no record of what the engine did or why; a crash mid-night loses the entire night's evaluations and transcript, since nothing before the last step is persisted.
- Confidence: high — the ordering is asserted, not inferred
- Severity: high
- Marked by authors: no

### F-04 — NightLock is a local file lock: mutual exclusion holds only on one machine
- Topics: CRT-01.2, CRT-02.2
- Evidence: The MSRV note reveals a `NightLock` built on `File::try_lock` (`Cargo.toml:7`). File locks coordinate processes on a single filesystem; nothing in the material describes any cross-machine coordination for the forge-writing, automerge-enabling operations in CRT-02.
- Failure: Two scheduled nights on two runners (or a retry while the first is hung, see F-07) both pass their local lock: competing drafts, duplicate PRs, and two actors racing to set branch protection and automerge on the same repository.
- Confidence: medium, inferred from the lock mechanism; no distributed-coordination claim exists to contradict
- Severity: high
- Marked by authors: no — the lock is mentioned only as an MSRV justification

### F-05 — CRT-01 promises the gate can be "rerun during replay"; CRT-02 shows the data replay needs is best-effort
- Topics: CRT-01.1, CRT-02.2
- Evidence: The gate is a separate pure crate so "its decision function can stay pure and be rerun during replay" (`crates/dream-gate/src/gate.rs:8`). But the inputs a replay needs — evaluator outputs, failure fingerprints, the night's decisions — exist only in the MemorySink record, which is a single best-effort write at the end of the night (`crates/dream-core/src/seams.rs:147`, CRT-02.2).
- Failure: After any incident involving a merged patch, the sink write has either failed or been pre-empted by the crash; there is nothing to replay against, so the advertised forensic safety net does not exist exactly when it is needed.
- Confidence: medium, inferred — the contradiction between the two claims is direct, the replay-input dependency is reasoned
- Severity: medium
- Marked by authors: no

### F-06 — publish_draft is a multi-step, non-atomic operation whose implementation may panic mid-flight
- Topics: CRT-02.2, CRT-02.1
- Evidence: `publish_draft` returns `PrOutcome` and sits in `persist.rs:291`, driving `GhForge`, whose role is a chain of distinct operations — push, PR creation, branch protection, automerge (CRT-02.1). The material states plainly: "a trait implementation can still panic" (`crates/dream-core/src/seams.rs:365`). No step is described as transactional or rolled back.
- Failure: A panic between push and protection (or between PR creation and automerge enable) leaves the target repo in a half-configured state — e.g. a branch pushed and automerge enabled with required checks unset — which then converts the next, otherwise ordinary PR into an ungated merge.
- Confidence: high that panics are possible and steps are separate; medium that no compensation exists (nothing in the material shows any)
- Severity: medium
- Marked by authors: no — the panic possibility is stated in passing, its consequence to publish atomicity is not flagged

### F-07 — No seam crossing has a deadline, timeout or cancellation story; a hung call stalls the night indefinitely

### F-08 — `Notifier::notify` returns no Result, so notification loss is invisible, and a panicking notifier aborts the run

### R-1 — An unvetted candidate merged into the client's repository through publish/automerge paths never exercised against a live forge, under a host order no driver enforces
- Topics: CRT-02.1, CRT-02.2
- Chain of events:
  1. A host driver runs a night; the supplied `Llm` returns a patch; the candidate is built and evaluators re-run (`crates/dream-core/src/candidate.rs:547`, `crates/dream-core/src/candidate.rs:552`).
  2. The host calls `publish_draft` and optionally `enable_automerge` (`crates/dream-core/src/persist.rs:291`).
  3. `GhForge`'s push, PR-creation and branch-protection code paths have never run against a live GitHub; the only test proves dyn-safety (`crates/dream-core/src/seams.rs:647`). A silent failure in `required_status_checks` or a check-name mismatch means the merge gate is empty in production even though the calls "succeeded".
  4. Independently, the evaluate-before-publish order exists only in crate docs; no driver in this repository enforces it, so any host variant that publishes on a failed or short evaluation reaches the same forge.
  5. GitHub merges the draft; unjudged, model-authored code lands on the client's branch; the client discovers it.
- Evidence: CRT-02.1 Debt — "push, PR creation and branch-protection paths have not been exercised against a live GitHub" (`crates/dream-core/src/seams.rs:647`); CRT-02.2 Open — "No driver in this repository enforces [the order], so the order is not machine-checked here" (`crates/dream-core/src/lib.rs:3`); the `Forge` trait surface includes `required_status_checks` and `enable_automerge` as independent methods (CRT-02.1); business text — "A full night still needs a host driver and model implementation", i.e. the publish-deciding glue is outside this repo's tests.
- Warning signs visible today: a single dyn-safety test on the only shipped forge implementation; no fake/in-memory `Forge` among the shipped implementations, so CI cannot execute the publish path at all; the Open on order enforcement.
- Confidence: high that the coverage gap exists (stated); medium — inferred — that it is this incident's cause.
- Severity: high

### R-2 — Model-authored code built and executed on the same host that holds authenticated push credentials, with no isolation stated anywhere in the material
- Topics: CRT-02.1, CRT-02.2
- Chain of events:
  1. The `Llm` produces patch blocks (CRT-02.2), and source gathering and repair also drive it directly (`crates/dream-core/src/source.rs:1040`, `crates/dream-core/src/source.rs:1299`).
  2. `LocalRunner` builds the candidate and re-runs evaluators as local commands (`crates/dream-core/src/runner.rs:48`, `crates/dream-core/src/candidate.rs:547`, `crates/dream-core/src/candidate.rs:552`); "the local runner needs its command dependencies".
  3. The same host's `GhForge` authenticates with git push and the gh CLI (`crates/dream-core/src/seams.rs:424`); "the GitHub forge needs git, gh and authentication".
  4. A candidate patch — or a patch that alters evaluator scripts the runner executes — runs with access to the gh token and the checkout. It exfiltrates client data or pushes commits directly, bypassing `publish_draft` entirely.
  5. The seams place "run untrusted commands" and "authenticated push" in one process; the only containment language anywhere is about the Notifier ("host contains faults"), never about candidate code.
- Evidence: co-location of `LocalRunner` and `GhForge` behind one host's `Box<dyn ...>` set (CRT-02.1, ADR-DE-005 line 30); credential requirements stated in the CRT-02 business text; `GhForge` shells out to `git push` and `gh` (`crates/dream-core/src/seams.rs:424`).
- Warning signs visible today: nothing in either document mentions a sandbox, privilege separation, or credential isolation for evaluator execution.
- Confidence: medium — the credential/exec co-location is stated; the absence of isolation is an argument from silence (inferred).
- Severity: high

### R-3 — The published PR outlived its record: publish and persistence are split across owners, memory writes are best-effort, and `notify` can panic or stall, so an automerging draft existed with no surviving internal trace
- Topics: CRT-02.1, CRT-02.2
- Chain of events:
  1. `publish_draft` returns `PrOutcome`; automerge is optionally enabled at that moment (`crates/dream-core/src/persist.rs:291`).
  2. Persistence of the night is a separate host responsibility (`crates/dream-core/src/seams.rs:365`) — a second write to a different owner, after the forge write.
  3. Memory writes are best effort; callers log and continue (`crates/dream-core/src/seams.rs:147`); the only real sink shipped is the local `JsonlSink` — one copy.
  4. `Notifier::notify` returns no `Result` (`crates/dream-core/src/seams.rs:320`), imposes no deadline, and an implementation can panic or stall the caller (CRT-02.1 Debt).
  5. A dropped write (disk full, permissions) or a panicking notify after publish leaves the forge still merging the PR while nothing internally links that merge to a night, a verdict, or an audit trail. The operator cannot tell the client what ran or why.
- Evidence: `crates/dream-core/src/seams.rs:147`, `crates/dream-core/src/seams.rs:320`, `crates/dream-core/src/seams.rs:365`; the Debt itself states the requirement with no mechanism — "verdict persistence must not depend on an uncontained notification"; the intended sequence puts record and notify last (`crates/dream-core/src/persist.rs:291`).
- Warning signs visible today: the no-`Result` invariant; the explicit panic/deadline debt; a single local file as the only durable sink.
- Confidence: high that each gap is real (all stated); medium — inferred — as this incident's cause.
- Severity: high

## Root causes, ranked

### R-1 — A patch can rewrite the tests that grade it, and the gate will accept the result
- Topics: GAT-01.5, GAT-01.3
- Chain of events: 1) The night is configured with evaluators such as `make test` or `pytest`; the policy builder reads each frozen command as shell words and protects only "path-like words and known baseline files" (`crates/dream-gate/src/guard.rs:586`). 2) The files that actually decide pass/fail are read indirectly — the document's own examples are a `Makefile` behind `make test` and a `conftest.py` behind `pytest` — and are invisible to the reader unless the operator named them in the config's `protected` globs or the host resolved them as extras (`crates/dream-gate/src/guard.rs:703`, `crates/dream-core/src/replay.rs:143`). 3) The model's patch stubs, weakens or deletes those test files; no protected path is touched, so the pre-apply guard passes (`crates/dream-core/src/candidate.rs:482`, `crates/dream-core/src/persist.rs:139`). 4) Evaluators run the modified tests and pass; the receipts carry the frozen command identity and pass validation, which checks identity, not what the command executed against (`crates/dream-gate/src/gate.rs:197`, `crates/dream-gate/src/gate.rs:218`). 5) The veto list is empty and the model claims ACCEPT; acceptance requires exactly that (`crates/dream-gate/src/gate.rs:489`). A change that never exercised the real test suite is merged into the client's repository.
- Evidence: "the reader cannot see files an evaluator reads indirectly (a Makefile behind make test, a conftest.py behind pytest); those must be named in the config's protected globs, or be baseline-tree files resolved by the host" (`crates/dream-gate/src/guard.rs:703`); "word_path: path-like words and known baseline files" (`crates/dream-gate/src/guard.rs:586`); "acceptance needs a claimed ACCEPT and an empty veto list" (`crates/dream-gate/src/gate.rs:489`). The business claim that a change touching "the files that decide whether it passes is rejected outright" holds only for files the policy actually names — nothing in the material shows a config that names test files.
- Warning signs visible today: the Debt paragraph in GAT-01.5 states the blind spot verbatim; the `Makefile`/`conftest.py` example is the authors naming the exact files that gate a typical repository.
- Confidence: high that the blind spot exists (stated by the authors); inferred that a patch exploited it — no concrete config is shown.
- Severity: high

### R-2 — Receipts are unattested and unbound to the evaluated tree, and the recorded tree hash predates evaluation
- Topics: GAT-01.2, GAT-01.4, GAT-01.3
- Chain of events: 1) The candidate run computes the tree hash it returns before build and evaluation run (`crates/dream-core/src/candidate.rs:547`). 2) Build and evaluator commands then execute in the worktree and can mutate it; the document states there is "no final hash check in `run`" (`crates/dream-core/src/candidate.rs:547`). 3) `decide` receives caller-supplied typed outcomes; it "does not authenticate execution or independently bind the receipt to the evaluated tree" (business section), and its receipt validation covers only the evaluator name, the stored digest field and a digest of the command text (`crates/dream-gate/src/gate.rs:197`, `crates/dream-gate/src/gate.rs:218`). 4) A receipt typed `Passed` is graded as a pass regardless of what actually ran or on which tree; raw streams are reclassified only by replay, after the fact (`crates/dream-core/src/replay.rs:467`). 5) Empty veto list plus claimed ACCEPT yields ACCEPT (`crates/dream-gate/src/gate.rs:489`); the change ships with a custody record — the prepared hash — that does not describe the tree that was evaluated.

Neither path attests real command execution" (`crates/dream-gate/src/gate.rs:218`, `crates/dream-core/src/replay.rs:467`); "the returned tree hash is prepared before build/evaluation; commands can mutate the tree afterwards without a final hash check in run" (`crates/dream-core/src/candidate.rs:547`).
- Warning signs visible today: three separate admissions — no attestation, no tree binding, stale hash — each already recorded as Debt in the material.
- Confidence: high that the gap exists (every element is stated); inferred that a forged or drifted receipt produced the incident.
- Severity: high

- Topics: GAT-01.3, GAT-01.5

# Post-mortem: nightly delivery and gate integrity

Scope note: this report is built only from the distilled topics (NIT-01…NIT-03) and the citations they carry. Where a mechanism is stated in the material, confidence is high; where I reason past it, I say so. The host driver that sequences phases, holds the lock and calls `capture` lives outside the audited code, so every "the host will…" claim below is a contract, not an enforced behaviour.

### R-1 — A crash after `Persisted` silently loses the night's publish; the restart marks the night Complete without ever asking the forge
- Topics: NIT-01.1, NIT-01.2, NIT-01.4, NIT-03.2
- Chain of events:
  1. The host records the verdict and journals phase `Persisted` before delivery, per the caller contract (`crates/dream-core/src/runstate.rs:615`).
  2. The host then pushes the candidate and opens the pull request. A crash, OOM kill or host bug lands anywhere in this window: before the push, between push and PR creation, or after the PR exists but before its URL or the ledger row is recorded.
  3. Nothing records the push, the PR URL or the ledger commit — journalling stops at `Persisted`.
  4. On restart, `begin` → `finished_night` sees `Persisted`, returns `AlreadyComplete` "do not re-run", and finalises to `Complete` best effort. No step reconciles against the forge.
  5. The night reports as done. The verdict was never delivered, or exists only as an orphaned branch / unrecorded PR. Detection depends on a human noticing an absence; the only remedy is a manual `reset_night`.
- Evidence: "`Persisted` is deliberately entered first, so a crash can lose a publish but never repeat one" (NIT-01.1, `crates/dream-core/src/runstate.rs:72`); "Nothing records the forge push or the ledger commit either, so a crash after `Persisted` loses that night's publish and the restart finalises the night to `Complete` without reconciling against the forge; recovery is `reset_night`" (NIT-01.1, `crates/dream-core/src/runstate.rs:401`); "a crash after `Persisted` can lose a publish, whether before the pull request exists or after it exists but before its URL or ledger row is recorded, and the restart finalises the night to `Complete` without asking the forge" (NIT-03.2, `crates/dream-core/src/persist.rs:298`, `crates/dream-core/src/runstate.rs:615`); the `AlreadyComplete` invariant fires on `Persisted` or `Complete` "whatever the run id says" (NIT-01.2, `crates/dream-core/src/runstate.rs:534`).
- Warning signs visible today: the material itself states the guarantee is at-most-once, i.e. may-be-zero, twice, in both NIT-01 and NIT-03; the business summary says "a crash can then lose a publish"; the NIT-01.3 restart diagram shows the restart path ending in `AlreadyComplete` with no forge contact anywhere in it.
- Confidence: high — the mechanism is stated outright; only which crash point occurred is inferred.
- Severity: high

### R-2 — The library enforces neither the night lock nor the persist ordering; two engines can run one night and both deliver
- Topics: NIT-01.1, NIT-01.2, NIT-01.4
- Chain of events:
  1. Both single-writer guarantees are host contracts: the host "is required to hold a `NightLock` across the whole night" and the `Persisted`-before-delivery ordering is "a documented caller contract".
  2. Nothing in this repository enforces either: `begin` does not take the lock and nothing calls `NightLock::acquire`; no code sequences `persist`.
  3. A second engine — a stale process after a redeploy, a second runner pointed at the same night directory, or a host implementation that skips the contract — starts the same night. `begin`'s read-modify-write of the attempts counter is unprotected inside the library, so both starts can read `attempts < budget` and both return a proceed verdict.
  4. Both engines evaluate, gate, persist, push and open PRs: duplicate or conflicting deliveries. The journal is written by rename, so the file is never torn, but the two processes' writes are last-writer-wins — one engine's `Persisted`/`Complete` can be overwritten by the other's earlier phase. `advance` never lowers the phase *per call*; nothing claims monotonicity across processes.
  5. Because delivery is unrecorded (R-1), nothing downstream notices the duplication.
- Evidence: "`begin` does not take it and nothing else in this repository calls `NightLock::acquire`, so an engine that skips it is not stopped here" (NIT-01.4 Open, `crates/dream-core/src/runstate.rs:261`); "the at-most-once ordering is a documented caller contract on `persist` … no code in this repository sequences it, so nothing here enforces it" (NIT-01.1 Tension, `crates/dream-core/src/runstate.rs:615`); the lock only "refuses while another cooperating holder owns that lock" and waits at most 500 ms (NIT-01.3, `crates/dream-core/src/runstate.rs:442`); "`advance` never lowers the phase" is stated as a per-call invariant (`crates/dream-core/src/runstate.rs:605`); the updated record is saved before `begin` returns (`crates/dream-core/src/runstate.rs:556`).
- Warning signs visible today: both an Open and a Tension in NIT-01 flag the unenforced contracts today; the same repository also contains no caller for `capture` (NIT-02.2 Open), confirming the entire driver is outside the audited code, so contract compliance is unverifiable from here.
- Confidence: high that enforcement is absent (stated); the concrete double-run and cross-process journal regression are inferred.
- Severity: high

### R-3 — The automerge self-reference guard is heuristic; a renamed engine repository is not recognised and the engine auto-merges its own candidate into itself
- Topics: NIT-03, NIT-03.1, NIT-03.2
- Chain of events:
  1. The engine repository is renamed or re-forked (reorganisation, client-specific fork).
  2. `auto_merge` is on in the protected config for that repository, and a night targets it.
  3. The `SelfReferential` test tries three heuristics: the slug, a config whose protected set covers the gate crates, and a checkout that contains them. A new slug fails the first; a config that does not cover the gate crates fails the second; a slim checkout without the crates fails the third.

- Evidence: the business summary disclaims it directly: "It does not establish that checks passed, the PR head matches the evaluated tree, or every renamed engine fork is recognised" (NIT-03); "The self-referential test has three heuristics for recognising engine targets: the slug, a config whose protected set covers the gate crates, and a checkout that contains them" (NIT-03.1, `crates/dream-core/src/automerge.rs:136`, `crates/dream-core/src/automerge.rs:144`); the `SelfReferential` refusal exists precisely to stop the engine merging itself and precedes even the ACCEPT check (`crates/dream-core/src/automerge.rs:114`); the flag being in protected config stops a *candidate* enabling it (`docs/adr/ADR-DE-006-automerge-is-an-option.md:30`) but nothing stops a legitimate operator config on a renamed repo.
- Warning signs visible today: the guard is described as heuristics, not identity; the business block already concedes renamed forks are unrecognised.
- Confidence: high that the guard is heuristic and the gap is real (stated); the exploit chain is its direct implication.
- Severity: high

## Root causes, most likely first

### R-1 — Fingerprint normalisation merges distinct failures, so a new failure is classified `Persisting` and its evidence veto is suppressed
- Topics: SEL-02.1, SEL-02.3, SEL-01.2
- Chain of events:
  1. A repo's baseline suite is already red with a known failure whose cause text contains a digit run (timeout seconds, exit code, error number).
  2. The candidate introduces a *different* failure. Normalisation replaces every ASCII digit run with a placeholder and truncates past 200 characters, so the candidate's cause normalises to the identical string as the baseline's.
  3. The identity — first 8 bytes of SHA-256 over `task, 0x1F, stage, 0x1F, normalised cause` — is therefore byte-identical.
  4. In the gate's two-step `advance`, a fingerprint present in the baseline manifest classifies as `Persisting`, not `New`.
  5. Only `New` records raise the evidence veto; persisting records never veto.
  6. Because the baseline case was already failing, `NoRegression` (pass-on-baseline → fail-on-candidate) does not apply, and the pairwise policies see comparable, tied evidence — no `Reject`.
  7. The candidate is selected with a new failure mode shipped to production. This is precisely the scenario the fingerprint check exists for ("a suite may already be failing on a known problem"), so the merge disables the only guard covering it.
- Evidence:
  - "ASCII digit runs become number placeholder" and the normalisation order (`crates/failure-fingerprint/src/lib.rs:190`); "Numeric causes and suffixes beyond 200 characters also deliberately collapse" (SEL-02.1, Debt, `lib.rs:190`).
  - Identity construction `lib.rs:357`, first-8-bytes at `lib.rs:365`.
  - "A match against a baseline failure suppresses this particular new-fingerprint veto" (SEL-02.1, Tension).
  - Classification by fingerprint-in-previous-manifest (`lib.rs:574`); only `New` records veto (`crates/dream-gate/src/pertest.rs:253`, `:261`); "persisting and fixed records never veto" (SEL-02.3).
  - `NoRegression` fires only on pass→fail (`crates/pairwise-gate/src/policy.rs:364`).
  - Sibling mechanisms in the same family: deterministic alias via the unit separator inside task/stage names (`alpha + sep + beta / gamma` ≡ `alpha / beta + sep + gamma`, `lib.rs:229`, `lib.rs:357`) and 64-bit truncation (`lib.rs:263`), with ADR-DE-004 listing "a collision seen in practice" as its review trigger.
- Warning signs visible today: the authors already marked the merges, the separator alias, and the 64-bit width as Debt/Tension; the ADR's own review trigger is this exact event. The already-red-suite path is stated as the design's core purpose (SEL-02 business section).
- Confidence: high — the suppression mechanism is stated outright; the specific incident path (already-red baseline, digit-bearing causes) is inferred from stated behaviour.
- Severity: high

### R-2 — Duplicate test names collapse last-wins, hiding candidate faults and regressions from every veto layer
- Topics: SEL-01.3, SEL-01.1
- Chain of events:
  1. A suite produces duplicate test names on a side (retries, parameterised cases, name collisions across shards).
  2. Per-test results are collected into a map keyed only by test name; the last duplicate wins.
  3. An earlier duplicate that faulted is overwritten, so the step-1 harness veto ("any fault … → BLOCKED-ENV") never fires.
  4. An earlier duplicate where the baseline passed and the candidate failed is overwritten by a later pass, so the new-fingerprint check and `NoRegression` see a pass.
  5. The candidate is selected carrying a hidden regression and/or an unreported environment fault.
- Evidence:
  - Debt at `crates/dream-gate/src/pertest.rs:208`: "each side is collected into a map keyed only by test name; the last duplicate wins and can hide a fault or regression".
  - Harness veto on any fault or baseline-test-missing-on-candidate (`pertest.rs:214`, `pertest.rs:232`); evidence veto on new fingerprints (`pertest.rs:253`, `:261`); pairings are built from the `TestOutcomes` (`pertest.rs:122`).
  - `NoRegression` rejects only pass-on-baseline → fail-on-candidate (`crates/pairwise-gate/src/policy.rs:364`).
  - The crate-level fault guard (`policy.rs:39`, `model.rs:283`) can only see faults that survive into the pairings.
- Warning signs visible today: flagged as Debt in SEL-01.3 with the words "hide a fault or regression"; the business section of SEL-01 already concedes the protection "depends on complete evidence with unique test identities".
- Confidence: high — the defect and its hiding effect are stated verbatim; the trigger (duplicate names appearing) is inferred.
- Severity: high

### R-3 — Credential-bearing cause text survives normalisation and is persisted to shared manifest files
- Topics: SEL-02.1, SEL-02.2, SEL-02.4
- Chain of events:
  1. A failure's cause text embeds a secret that is shorter than 16 characters or punctuation-separated (a short token in an error line, credentials in a message).
  2. Normalisation replaces only paths, identifier runs ≥ 16 chars, and digit runs; it "is neither a secret filter", so the secret survives into the normalised cause.
  3. `advance` stores the normalised cause in the record.
  4. The cross-night path writes per-repo manifest files into a shared state directory and reloads them each night.
  5. Any reader of the shared directory obtains the credential-bearing cause text; the JSON reader additionally accepts records with unnormalised causes, so other writers can persist raw cause text unmodified.
  6. Credential leak becomes a security incident costing the client.
